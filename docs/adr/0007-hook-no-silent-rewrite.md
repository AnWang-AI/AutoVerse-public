# ADR-0007：PreToolUse 钩子是中间件，可 deny 但默认不静默改写 tool_input

> 决策状态：已采纳（2026-06）
> 当前事实来源：相关 `docs/architecture/`、`docs/design/` 和代码实现。
> 维护规则：记录决策和后果；不要把 ADR 当作实施计划或当前 API 参考。

- **相关设计**：[Hooks 参考](../reference/hooks.md)、[工具与权限设计](../design/tools-and-permissions.md)

## 背景（Context）

`PreToolUse` 钩子作为 `ToolDispatcher` 中间件链中权限之前的一环，包裹一次工具调用。问题是：除了放行 / `deny`，钩子是否应被允许**改写** `tool_input`（如自动规范化路径、补全默认参数）？

改写需求真实且高频；但中间件直接改写模型未察觉的参数，会让"模型以为执行了 A、实际执行了 A'"。

## 决策（Decision）

**钩子可放行或 `deny`（并解释），但默认不改写 `tool_input`。** 当前实现只支持放行、`deny`、`reason` 和 `additionalContext`；要调整参数的常规路径是：钩子 `deny` 并说明，模型显式调整后重试。若未来提供改写能力，必须作为**显式 opt-in 能力**接入，且**强制把改写后参数回显给模型**，绝不静默改写。

## 理由（Rationale）

- 中间件式 `deny` 与权限正交且语义干净——拦截点明确、可短路、可 fail-closed。
- 允许静默改写会制造最隐蔽的 bug：模型认知与实际执行分叉，违反反馈完备性。这类"沉默偏差"难以排查。
- 反方的"自动规范化/补全"需求真实，故仅作为未来可选方向保留——必须以 opt-in + 强制回显承接，而非默认开放静默改写。

## 后果（Consequences）

- 默认行为安全可推理：模型看到的参数 = 实际执行的参数。
- 当前规范化类需求应通过 `deny` + 明确原因让模型重试。未来若接入改写能力，也必须多一次模型可见的反馈往返。
- 钩子层与权限层保持各自独立记录（`HOOK_BLOCKED` vs `PERMISSION_DENIED`），便于事后区分。

## 可证伪边界（何时重新审视）

若回显机制落地后实测模型仍能稳定理解被改写的参数、且无认知分叉的 bug，则可考虑放宽默认（允许带回显的改写成为默认）；反之保持默认禁止。
