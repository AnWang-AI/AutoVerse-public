# ADR-0010：用"四维度"作为工作流的统一设计语言

> 决策状态：已采纳（2026-06）
> 当前事实来源：相关 `docs/architecture/`、`docs/design/` 和代码实现。
> 维护规则：记录决策和后果；不要把 ADR 当作实施计划或当前 API 参考。

- **相关设计**：[工作流参考](../reference/workflows.md)、[子代理与工作流设计](../design/subagents-and-workflows.md)

## 背景（Context）

AutoVerse 要支持多种编排机制（普通对话、目标驱动 `/goal`、固定阶段流水线 `/commit`、多代理评分循环 `/coordinate` 等），且要能持续新增。问题是：用什么概念框架统一描述、推演、区分这些工作流？是为每种工作流各写一套定义结构，还是抽出一组共同维度？

## 决策（Decision）

**所有编排机制都分解为四个正交维度——触发（trigger）× 编排（orchestration）× 推进（advancement）× 终止（termination）——`WorkflowDefinition` 以此为 schema；新工作流靠"填这张四维度表"推演，填完实现路径即被唯一确定。**

## 理由（Rationale）

四维度同时提供三种能力：

- **描述力**：任一编排机制都能填进四维度表。
- **推演力**：填完表，实现路径（runner / phases / gate）即被当前 `WorkflowDefinition` schema 唯一确定。
- **区分力**：`/commit` 与 `/coordinate` 都经由多阶段/多代理管线推进，但终止维度不同（`FIXED_PHASES_DONE` vs `SCORE_THRESHOLD`），四维度让此区别一目了然，避免被误当重复而错误合并。

关键在于这是一门**可证伪**的设计语言：若一个机制填不进四维度表，结论是"它不是工作流，或四维度不正交需复审"，而非用万能咒强行解释一切。这正是健康抽象该有的自检能力。

## 后果（Consequences）

- 新增工作流是"填表 + 实现"，主循环与 gate 遍历代码不触碰。
- 四个维度彼此正交，可分别演进（如新增终止判据类型只动终止维度）。
- 代价：设计者需先理解四维度框架；个别真正新颖的机制可能需要为"填不进"做诊断而非直接实现。

## 可证伪边界（何时重新审视）

若**反复**出现合理的编排机制系统性地填不进四维度（而非个别例外），说明维度选取有误或不正交，应重新归纳维度集，而不是硬塞。个别例外则按"它不是工作流"处理。
